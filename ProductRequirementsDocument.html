1. Executive Summary

ProperT is a modern, high-performance real estate platform designed to streamline property discovery and transaction management. By leveraging a cutting-edge tech stack, it solves the fragmentation in the market, offering real-time communication, instant booking, and hyper-local discovery.

2. User Personas

  • The Agent (Alex): Needs high-volume management tools, lead qualification, and calendar automation.
  • The Private Seller (Sarah): Needs simplicity, guidance, and direct access to buyers without intermediaries.
  • The Seeker (David): Needs speed, accurate location data, rich media, and instant gratification (booking/chat).

3. Technical Architecture & Best Practices Strategy

3.1 Core Tech Stack

Based on deep research into scalable, maintainable, and type-safe applications, the following stack is mandated:

  • Frontend: Next.js 14+ (App Router)
    • Why: Server-Side Rendering (SSR) for SEO (critical for real estate listings), fast initial load, and widely supported.
    • Language: TypeScript (Strict Mode).
    • State Management: Zustand (Global client state) + TanStack Query (React Query) (Server state/Caching).
      • Best Practice: Avoid Redux complexity. Use React Query to handle caching, deduping, and background updates of listing data.
    • UI Framework: Tailwind CSS + Shadcn/UI (Radix Primitives).
      • Why: Accessible, customizable, and lightweight compared to Material UI.
    • Forms: React Hook Form + Zod (Schema Validation).
  • Backend: NestJS
    • Why: Modular architecture (Angular-like dependency injection), highly testable, and robust for enterprise-grade apps.
    • Language: TypeScript.
    • Validation: class-validator + class-transformer (DTO pattern).
    • Real-time: Socket.io gateway (for Chat & Notification).
  • Database: PostgreSQL
    • Why: The gold standard for data integrity.
    • Critical Extension: PostGIS.
      • Best Practice: Do NOT calculate distances in code. Use PostGIS spatial queries (ST_DWithin, ST_Distance) for high-performance "Propeties Near Me" features.
    • ORM: Prisma.
      • Why: Best-in-class TypeScript safety. (Note: Will use raw queries or extensions for complex PostGIS operations).
  • Infrastructure & Services:
    • Docker: Containerization for consistent dev/prod environments (Frontend, Backend, Postgres, Redis).
    • Redis: For caching frequently accessed data (e.g., recommend properties) and managing Socket.io sessions.
    • BullMQ (Redis): Asynchronous Job Queue for heavy tasks (Image resizing, sending emails) to strictly keep the API response time low.
    • Storage: AWS S3 (or MinIO for local dev) for high-res images/videos. Storing files in the DB is an anti-pattern.

4. Functional Requirements

4.1 Advanced Search & Discovery (Geo-Spatial)

  • FR-01: Implementation of PostGIS for location queries.
  • FR-02: "Search this area" map feature. Frontend sends Polygon coordinates; Backend queries DB for points inside polygon.
  • FR-03: Filters: Dynamic query generation (Price, Type, Amenities).

4.2 Listing Management

  • FR-04: Multi-step wizard for uploading properties:
    • Step 1: Basic Info (Address with Auto-complete).
    • Step 2: Details & Amenities (Structured Data).
    • Step 3: Media Upload (Direct-to-S3 signed URLs to avoid bottling the backend).
    • Step 4: Availability Configuration.

4.3 Smart Tour Scheduling (Viewing Management)

This module requires a strict state machine to prevent overbooking.

  • FR-05 (Availability Model): Listings have AvailabilitySlots.
    • Structure: Recurring rules (e.g., "Every Mon 9-5") OR Specific Date Overrides.
  • FR-06 (Concurrency Control):
    • Best Practice: Use Database Transactions (Prisma $transaction) when confirming a booking to ensure the slot wasn't snatched milliseconds prior.
  • FR-07: Status workflow: PENDING -> CONFIRMED -> COMPLETED / CANCELLED.

4.4 Internal Messaging (Real-Time)

  • FR-08: WebSockets for instant message delivery.
  • FR-09: Persistence: Messages stored in Postgres, but active conversations cached in Redis for speed.
  • FR-10: Contextual Chat: Every conversation is linked to a ListingID to give context (e.g., "Hi, is [Listing 123] available?").

5. Data Model Recommendations (PostgreSQL Schema)

5.1 Users & Auth

model User {
  id        String   @id @default(uuid())
  email     String   @unique
  password  String   // Hashed (Bcrypt/Argon2)
  role      UserRole @default(SEEKER) // ADMIN, AGENT, OWNER, SEEKER
  
  // Relations
  listings  Listing[]
  bookings  Booking[]
  messages  Message[]
}

enum UserRole {
  SEEKER
  OWNER
  AGENT
  ADMIN
}

5.2 Properties (Spatial)

model Listing {
  id          String   @id @default(uuid())
  title       String
  description String
  price       Decimal  @db.Decimal(12, 2) // Best practice for money
  
  // Location - In real implementation, use raw SQL for PostGIS geometry
  latitude    Float
  longitude   Float
  address     String
  
  // Media
  images      String[] // Array of S3 URLs
  
  // Metrics
  views       Int      @default(0)
  
  ownerId     String
  owner       User     @relation(fields: [ownerId], references: [id])
  
  bookings    Booking[]
  availabilities Availability[]
  
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
  
  @@index([price])
  @@index([ownerId])
  // @@index([location], type: Gist) -- PostGIS index
}

5.3 Scheduling & Bookings

model Availability {
  id        String   @id @default(uuid())
  listingId String
  listing   Listing  @relation(fields: [listingId], references: [id])
  
  dayOfWeek Int      // 0-6
  startTime String   // "09:00"
  endTime   String   // "17:00"
}

model Booking {
  id        String   @id @default(uuid())
  listingId String
  listing   Listing  @relation(fields: [listingId], references: [id])
  
  seekerId  String
  seeker    User     @relation(fields: [seekerId], references: [id])
  
  startTime DateTime
  endTime   DateTime
  status    BookingStatus @default(PENDING)
  
  createdAt DateTime @default(now())
}

enum BookingStatus {
  PENDING
  CONFIRMED
  REJECTED
  CANCELLED
}

5.4 Messaging

model Conversation {
  id        String   @id @default(uuid())
  listingId String?
  
  participants UserConversation[]
  messages     Message[]
  updatedAt    DateTime @updatedAt
}

model Message {
  id             String   @id @default(uuid())
  conversationId String
  conversation   Conversation @relation(fields: [conversationId], references: [id])
  senderId       String
  sender         User     @relation(fields: [senderId], references: [id])
  content        String
  read           Boolean      @default(false)
  
  createdAt      DateTime     @default(now())
}

6. UI/UX Guidelines

  • Performance:
    • Implement Image Optimization (next/image) for all property photos.
    • Skeleton Loaders for listing cards while fetching data.
    • Virtualization for map pins if displaying thousands of points.
  • Accessibility (a11y):
    • Ensure all forms are keyboard navigable.
    • ARIA labels for interactive map elements.

7. Security NFRs

  • JWT Strategies: Use Access Token (Short-lived) + Refresh Token (HttpOnly Cookie, Long-lived). This prevents XSS attacks from stealing tokens.
  • Input Sanitization: Global Validation Pipe in NestJS to strip malicious properties.
  • Rate Limiting: Protect API routes (especially Login and Search) using ThrottlerModule.
